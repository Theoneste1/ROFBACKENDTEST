# P0-05 — Cloudflare R2 upload and download verification

**Status: PENDING.** Tooling and automated tests are ready (S3Mock in CI). The live check against the production bucket
has **not** been run and needs the owner's explicit approval. A passing S3Mock test is not proof that R2 works.

Definition of done (`IMPLEMENTATION_TRACKER.md`): an object written to `rof-files`, its download byte-identical, and
the API's start-up log naming the R2 bucket.

## 2. The tool

`npm run storage:verify -- --env-file .env.r2.local …` (`scripts/storage-verify.ts`, logic in
`src/common/storage/storage-verification.ts`). It uses the **application's own `S3StorageDriver`** with the same
`S3_*` settings as the API.

| Safety rule | How |
|---|---|
| Plan only by default | without `--execute` it prints the plan and sends nothing |
| Right bucket | `--execute` and `--delete-key` require `--confirm-bucket <name>` equal to `S3_BUCKET` in the env file |
| Credentials never committed or printed | env file must be git-ignored (e.g. `.env.r2.local`, matched by `.env.*.local`) or outside the repository; only that file is read; output shows the bucket and a masked endpoint (`0123….r2.cloudflarestorage.com`) |
| One object, dedicated prefix | writes/deletes only `p0-05-verification/<UTC timestamp>-<random>/probe.txt`; every write and delete checks that exact shape |
| No overwrite | the key is new per run and must not exist before the upload |
| Existing files untouched | the rest of the bucket is **listed** before and after (read-only); every existing object must still be present with the same size and ETag. Only counts and a hash are printed, never other keys |
| Clean-up only when approved | the probe is deleted only with `--cleanup` (or later with `--delete-key <key>`) |
| Synthetic content | ~64 KiB of text: a header plus random base64; no user data |

Checks (`--execute`): 1 `HeadBucket` (as `/health`) · 2 inventory before · 3 key is new · 4 upload through the driver
(`text/plain`) · 5 `HEAD`: size, content type, ETag = MD5 of content · 6 download through the driver, SHA-256
identical · 7 exactly one object under the run prefix · 8 missing key → "not found" (API 404) · 9 delete through the
driver and confirm gone (`--cleanup` only) · 10 inventory after: nothing removed or changed.

## 3. Live verification procedure (requires approval — not run)

**Stage A — tool against R2 (one synthetic object).**

1. Owner, Cloudflare → R2 → *Manage API tokens* → **Create a temporary token**: *Object Read & Write*, **only bucket
   `rof-files`**, short TTL. (Recommended over reusing the API's production key: it can be revoked afterwards without
   touching Render.) Needed operations: `HeadBucket`, `ListObjectsV2`, `HeadObject`, `PutObject`, `GetObject`, and
   `DeleteObject` for clean-up.
2. Owner creates `.env.r2.local` in the repository folder (git-ignored), never pasted in chat:
   ```
   S3_BUCKET=rof-files
   S3_REGION=auto
   S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
   S3_ACCESS_KEY_ID=<temporary token access key id>
   S3_SECRET_ACCESS_KEY=<temporary token secret>
   S3_FORCE_PATH_STYLE=true
   ```
3. Plan: `npm run storage:verify -- --env-file .env.r2.local` (no network).
4. Run (after approval): `npm run storage:verify -- --env-file .env.r2.local --execute --confirm-bucket rof-files --cleanup --json <file outside the repo>`
   — or without `--cleanup` to keep the object for inspection in the Cloudflare dashboard, then
   `--delete-key <key> --confirm-bucket rof-files`.
5. Owner revokes the temporary token and deletes `.env.r2.local`.

**Stage B — the deployed API names R2 (read-only, owner).** Render → Logs after the latest deploy: expect
`File storage: S3-compatible bucket "rof-files" at <account>.r2.cloudflarestorage.com (region auto, path-style on)`.
A `File storage: LOCAL disk` warning means R2 is not in use. `GET /health` → `"storage":"up"`.

**Stage C — optional, separate approval.** An upload and download through the production API (as a mentor or
administrator) also exercises authorization and the `FileObject` record, but writes to the production database and
needs a production login. Not required for P0-05's definition of done.

Not affected by any stage: production environment variables, the bucket's settings, and every existing object.
