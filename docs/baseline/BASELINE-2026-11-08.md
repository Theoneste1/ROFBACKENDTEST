## 5. API surface at the baseline

Snapshot: [api-snapshot-2026-11-08.json](api-snapshot-2026-11-08.json) — **format v2** (fingerprint `34d76bdd8e98257b…`),
generated from the committed `docs/api/openapi.json` (unchanged since `a8df186`). Format v2 replaced the first
version (fingerprint `aad0b4fb…`) after independent review (PR #7) found that v1 missed nested, typed and enum
changes; v1 also did not record nullability or request constraints.

| Measure | Value |
|---|---|
| Operations | 202 (GET 103 · PATCH 48 · POST 42 · DELETE 8 · PUT 1) |
| Paths | 180 (several operations share a path) |
| Groups (tags) | 29 |
| Public operations (no authentication) | 16 |
| Component schemas | 54 (request DTOs + `Error`) |
| Recorded in schemas | 595 nullable markers, 44 enums, `$ref`s, arrays, `anyOf` unions, request constraints |
| Base path | `/api/v1` (health at `/health`) |

**What the snapshot records** — per operation: method and path, operation ID, tags, roles (`x-roles`),
public/protected, parameters (location, required, schema), request body (required, content types, schema) and every
response status with its content types and schema. Schemas are normalised recursively: `$ref`, arrays and their
items, objects (properties, required list, `additionalProperties`), unions (`anyOf`/`oneOf`/`allOf`), and for scalar
values the type, format, enum values, `nullable` and constraints (`minLength`, `maxLength`, `minimum`, `maximum`,
exclusive bounds, `pattern`, `minItems`, `maxItems`). Response shapes come from the recorded responses
(`docs/api/response-schemas.json`).

**How changes are classified** — the comparison follows `$ref`s and arrays to any depth (recursive schemas are
handled once per pair) and treats requests and responses differently, because a change that is safe for data the
client *reads* can break data the client *sends*, and vice versa:

| Change | Request (client sends) | Response (client reads) |
|---|---|---|
| Field removed (any depth) | **breaking** — the API rejects unknown fields | **breaking** |
| New field | optional: additive · required: **breaking** | additive |
| Optional ↔ required | → required: **breaking** · → optional: additive | no longer always present: *review* · now always present: additive |
| Type change (incl. object ↔ array) | **breaking**; `integer` → `number`: additive | **breaking** (incl. `integer` → `number`) |
| `nullable` | null no longer accepted: **breaking** · newly accepted: additive | may now be null: **breaking** · no longer null: additive |
| Enum | value removed or new restriction: **breaking** · value added / restriction removed: additive | value added / restriction removed: *review* · value removed: additive |
| Format | added or changed: **breaking** · removed: additive | changed: **breaking** · removed: *review* · added: additive |
| Constraints | tightened or added (incl. `pattern`): **breaking** · loosened or removed: additive | not compared (informational) |
| Union variants | removed: **breaking** · added: additive | added: *review* · removed: additive |

Operation level: operation removed, **operation ID changed**, roles narrowed, public → protected, parameter removed
or newly required, request body becoming required / added as required / removed, response status or content type
removed → **breaking**. Operation becoming public → *review* (security). New operations, statuses, content types,
optional parameters and widened roles → additive.

**Limitations (known, accepted for the baseline):**

- The comparison is only as complete as the OpenAPI document. Response shapes are inferred from responses recorded during e2e tests, so a field the tests never returned is not in the contract; DTO validation rules not exported to OpenAPI (custom validators, cross-field rules) are invisible.
- `allOf` compositions are compared as a whole (any change → *review*), not field by field. Union variants are compared by exact shape, so a changed variant shows as one removed plus one added.
- Response constraints, defaults, descriptions and examples are not compared. `readOnly`/`writeOnly`, headers, cookies and security-scheme details are not recorded.
- Path renames appear as one removed and one added operation (breaking), not as a rename.
- Classification follows general client-compatibility rules; some *review* items (e.g. a new response enum value) are safe for this frontend, which handles unknown values, and some additive items may still need coordination. Human review of the report remains required.
- The tests run with `node --test`; they are not yet part of `npm test` or CI (adding them is a separate, small CI change).
